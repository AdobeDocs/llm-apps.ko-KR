# LLM 앱 설명서

Adobe LLM 앱에 대한 작업 지향, 확인 가능한 공개 설명서를 만듭니다.

## Source 진상 규명

다음 순서로 제품 클레임 확인:

1. `https://experience.adobe.com/#/@llmapps/llm-apps/`의 현재 프로덕션 UI
2. 작업 영역에서 사용할 수 있는 현재 UI 및 API 구현
3. 현재 공개 SDK 및 보일러플레이트 동작
4. 기존 공개 설명서

프로덕션이 소스 또는 계획과 충돌하는 경우 프로덕션을 문서화하고 불일치를 보고합니다. 예정된 워크플로를 현재 사용 가능한 상태로 게시하지 마십시오.

## 모든 작업 시작

1. `help/main-toc/TOC.md`을(를) 읽습니다.
2. 대상 문서 및 직접 관련 문서를 읽습니다.
3. [content-model.md](content-model.md)을 사용하여 콘텐츠를 분류합니다.
4. 확인이 필요한 UI 레이블, URL, 명령 및 계약을 식별합니다.
5. 페이지 전체에서 엔드투엔드 샘플 및 용어를 일관되게 유지합니다.

## 작성 규칙

- 자동 앱 만들기(**[!UICONTROL 내 앱을 자동으로 빌드]** 흐름)를 통해 처음 사용자를 유도합니다.
- 구현 주제가 아닌 사용자 여정 및 결과에 대한 탐색을 구성합니다.
- 각 안내서의 시작 부분 근처에 여정 순서를 지정하고 다음 공유 단계를 제공합니다.
- 고객 응대 문서에서는 내부 코드 이름(예: &quot;온보딩 에이전트&quot;)을 사용하지 마십시오. 이 기능은 제품 UI에 노출되지 않습니다. 일반적으로 설명하고(예: &quot;플랫폼&quot;) 컨트롤에 대해 **[!UICONTROL 내 앱을 자동으로 빌드]**&#x200B;와 같은 정확한 UI 복사본을 사용합니다.
- [!DNL Adobe LLM Apps]은(는) 플랫폼에 종속되지 않습니다. MCP 서버는 [!DNL ChatGPT]뿐만 아니라 지원되는 모든 LLM 플랫폼에서 작동합니다. [!DNL ChatGPT]이(가) 유일한 대상이었던 것처럼 일반 또는 설명 주장을 표현하지 마십시오(예를 들어 &quot;ChatGPT&quot;만 사용하는 것보다 &quot;[!DNL ChatGPT]&quot;과(와) 같은 지원되는 LLM 플랫폼을 선호함). 현재 [!DNL ChatGPT]에만 해당되는 콘텐츠에 명시적으로 [!DNL ChatGPT] 이름만 있습니다. ChatGPT 가이드의 전용 [테스트](/help/guides/test-in-chatgpt.md), 직접 교차 링크/절차 단계, [!DNL ChatGPT]별 참조 또는 문제 해결 콘텐츠입니다.
- 사용자가 처음 접했을 때의 기술적 개념을 설명하고 더 깊은 개념이나 참조 자료에 연결합니다.
- 튜토리얼을 선형, 방법 안내서를 작업 중심, 참조 페이지를 사실대로 유지하십시오.
- 독자가 현재 작업에 필요한 정보만 포함하고, 짧고 직접적인 문장을 선호합니다.
- 여정 전체에서 하나의 대표 앱을 사용합니다.
- 생성된 scaffold와 프로덕션 준비 통합을 구별합니다.
- 내부 작업자 이름, 데이터베이스 필드, 구현 티켓 및 불안정한 파이프라인 세부 정보를 사용하지 마십시오.
- 안내선에 필드 표를 복제하지 마십시오. 참조 링크입니다.
- `[!DNL]`, ``, `[!IMPORTANT]`, `[!NOTE]` 및 `[!TIP]` Experience League Frontmatter와 지시문을 유지합니다.
- 루트 상대 내부 링크 사용: `/help/...`.
- 제품 레이블에 달리 언급되지 않는 한 제목 및 제목에 대소문자를 사용하십시오.
- 화면과 상태를 설명하는 설명 이미지 대체 텍스트를 사용합니다.

## 보호된 PM 승인 이야기

`help/overview/overview.md`에서 다음 섹션은 PM 승인되었습니다.

- **LLM 앱으로 수행할 수 있는 작업**
- **LLM 앱이 중요한 이유**

제목, 글머리 기호, 문구, 순서 및 주장을 그대로 유지합니다.
일반 문서 작성 중에 길이를 줄이거나, 다시 작성하거나, 다시 구성하지 마십시오.
업데이트. 사용자가 명시적으로 요청하고
새 복사본이 PM 승인되었음을 확인합니다.

## 보안 요구 사항

- 자격 증명, 토큰, 개인 URL, 개인 데이터, 내부 호스트 이름 또는 고객 식별자를 포함하지 마십시오.
- 하드 코딩되지 않은 관리되는 구성에서 로드된 비밀을 표시합니다.
- 외부 서비스에 HTTPS가 필요합니다.
- 외부 입력 및 업스트림 응답 유효성 검사.
- 안전한 DOM API를 사용하여 외부 값을 렌더링합니다. `innerHTML`(으)로 보간하지 않는 것이 좋습니다.
- 최소 권한 GitHub 앱, API, CSP, CORS 및 브라우저 권한을 추천합니다.
- 안전한 사용자 대면 오류를 사용하고 민감한 데이터에 대한 로깅을 피하십시오.

## 스크린샷 워크플로

새로 고치거나 새로 고친 이미지의 경우 [screenshots.md](screenshots.md) 및 [screenshot-manifest.md](screenshot-manifest.md)을(를) 따르십시오.

기본 워크플로우는 사용자가 만든 프로덕션 캡처 팩을 사용합니다.

1. `docs-captures/<run-id>/`에서 스크린샷을 찾거나 사용자가 제공한 폴더를 사용하십시오.
2. 모든 PNG, JPEG 및 WebP 파일을 인벤토리와 시각적으로 검사합니다. 파일 이름에만 의존하지 마십시오.
3. 표시되는 UI 콘텐츠를 사용하여 스크린샷을 매니페스트 상태와 일치시킵니다.
4. 설명서를 변경하기 전에 보고서가 누락되었거나, 중복되었거나, 모호하거나, 오래되었거나, 안전하지 않은 캡처입니다.
5. 소스 캡처를 변경하지 않고 유지합니다.
6. `help/assets/` 아래의 안정적인 매니페스트 파일 이름을 사용하여 정리된 최종 복사본을 만드십시오.
7. 실제 캡처된 프로덕션 워크플로우와 일치하도록 자습서 및 관련 안내서를 업데이트합니다.
8. 정확한 대체 텍스트를 추가하고 설명서 유효성 검사를 실행합니다.

에이전트 안내식 브라우저 캡처는 선택적 대체 항목으로 유지됩니다. 브라우저 상태나 자격 증명을 저장하지 않으며, CI에서 프로덕션 변경 스크린샷 캡처를 실행하지 마십시오.

&quot;스크린샷에서 문서를 업데이트&quot;하라는 메시지가 표시되는 경우:

- 명시적으로 선택한 최신 캡처 폴더를 소스로 처리합니다.
- 앱 플로우 또는 스크린샷 매핑이 실제로 모호한 경우에만 묻습니다.
- 원시 캡처 폴더를 커밋하지 마십시오.
- 명시적 승인 없이 소스 캡처를 삭제하거나 수정하지 마십시오.
- 작업을 방해하지 않고 중요한 정보를 제거할 수 없는 경우 안전한 재캡처를 요청합니다.

## 리뷰 아카이브 구축

공유 가능한 오프라인 HTML 사이트 및 ZIP 아카이브를 생성합니다.

```bash
node .cursor/skills/llm-apps-docs/scripts/build_review_bundle.mjs
```

빌드는 저장소 내부가 아니라 저장소 옆에 작성됩니다. 단지 포함
게시된 문서 및 정리된 에셋은 Experience League 지침을 전환합니다.
오프라인 검토의 경우 및 해당 스타일이 최종 경험이 아님을 확인합니다.
리그 렌더링.

## 유효성 검사

실행:

```bash
python3 .cursor/skills/llm-apps-docs/scripts/validate_docs.py
```

나누기 전에 누락된 모든 내부 문서, 누락된 자산, 잘못된 루트 상대 경로 및 누락된 프론트마터 필드를 수정하십시오.

또한 다음을 확인하십시오.

- UI 레이블 및 스크린샷이 프로덕션과 일치합니다.
- 스크립트 및 위젯 URL 예는 안내서 및 참조 간에 일치합니다.
- 명령은 현재 상용구와 일치합니다.
- 새 페이지는 목차에서 연결됩니다.
- 사용 가능한 경우 Adobe 문서 유효성 검사 워크플로우가 통과합니다.
